# GraphQL Security POC — Full Plan

## 1. Objectives

Build a runnable application demonstrating progressively stronger GraphQL security:

```text
Authentication
      │
      ▼
Named GraphQL operations
      │
      ▼
Operation allow-list
      │
      ▼
Operation → root-field validation
      │
      ▼
Permission-based authorization
      │
      ▼
Tenant / ownership authorization
      │
      ▼
Sensitive field authorization
      │
      ▼
PostgreSQL
```

The POC should explicitly demonstrate why an operation-name allow-list is useful but insufficient by itself.

Everything should run locally from the monorepo.

# 6. GraphQL schema

Start with something like:

```graphql
type Query {
    order(id: ID!): Order
    myOrders: [Order!]!
    orders: [Order!]!
}

type Mutation {
    createOrder(input: CreateOrderInput!): Order!
    updateOrder(id: ID!, input: UpdateOrderInput!): Order!
    cancelOrder(id: ID!): Order!
    deleteOrder(id: ID!): Boolean!
}

type Order {
    id: ID!
    description: String!
    amount: Float!
    status: OrderStatus!
    customer: User!
    internalNotes: String
}

type User {
    id: ID!
    username: String!
}

input CreateOrderInput {
    description: String!
    amount: Float!
}

input UpdateOrderInput {
    description: String
    amount: Float
}

enum OrderStatus {
    OPEN
    CANCELLED
    COMPLETED
}
```

# 7. Authentication

The React application authenticates against Keycloak.

```text
Browser
   │
   ▼
Keycloak login
   │
   ▼
Access token
   │
   ▼
React
   │
   │ Authorization: Bearer <JWT>
   ▼
Spring Boot
```

Spring Security operates as an OAuth2 resource server and validates the JWT.

From the authenticated principal we'll construct:

```java
public record CurrentUser(
    String id,
    String username,
    String tenantId,
    Set<Role> roles
) {}
```

One important rule for the architecture:

**React never determines whether an operation is authorized.**

The UI can hide unavailable functionality for usability, but every security decision is enforced by Spring.

---

# 8. GraphQL operation-name security

This is the first GraphQL-specific security layer.

Require named operations:

```graphql
query GetOrder($id: ID!) {
    order(id: $id) {
        id
        description
    }
}
```

Maintain an allow-list:

```text
GetOrder
GetMyOrders
GetOrders

CreateOrder
UpdateOrder
CancelOrder
DeleteOrder
```

Spring GraphQL instrumentation/interception determines the selected operation.

Requests with:

```text
anonymous operation
unknown operation
invalid operationName
```

are rejected.

---

# 9. Demonstrate the operation-name vulnerability

This is an intentional part of the POC.

Allowed:

```graphql
query GetOrder {
    order(id: "123") {
        id
    }
}
```

But an attacker sends:

```graphql
query GetOrder {
    orders {
        id
        amount
        internalNotes
    }
}
```

The operation-name check sees:

```text
GetOrder
```

in both cases.

The POC should contain an automated test demonstrating that **operation-name allow-listing alone doesn't secure GraphQL**.

---

# 10. Operation → GraphQL capability mapping

Introduce a stronger policy:

```text
GetOrder
    → Query.order

GetMyOrders
    → Query.myOrders

GetOrders
    → Query.orders

CreateOrder
    → Mutation.createOrder

UpdateOrder
    → Mutation.updateOrder

CancelOrder
    → Mutation.cancelOrder

DeleteOrder
    → Mutation.deleteOrder
```

Therefore:

```graphql
query GetOrder {
    orders {
        id
    }
}
```

is rejected because:

```text
operation:      GetOrder
expected:       Query.order
actual:         Query.orders
```

This gives us structural validation independent of the client-controlled operation name.

# 11. Application permissions

Represent capabilities explicitly:

```java
public enum Permission {

    ORDER_READ,
    ORDER_READ_OWN,

    ORDER_CREATE,

    ORDER_UPDATE,
    ORDER_UPDATE_OWN,

    ORDER_CANCEL,
    ORDER_CANCEL_OWN,

    ORDER_DELETE,

    ORDER_READ_INTERNAL
}
```

Roles map to permissions.

For example:

```text
CUSTOMER

ORDER_READ_OWN
ORDER_CREATE
ORDER_UPDATE_OWN
ORDER_CANCEL_OWN
```

```text
SUPPORT

ORDER_READ
ORDER_UPDATE
```

```text
ADMIN

ORDER_READ
ORDER_CREATE
ORDER_UPDATE
ORDER_CANCEL
ORDER_DELETE
ORDER_READ_INTERNAL
```

Application code checks permissions rather than hard-coding:

```java
if (role == ADMIN)
```

throughout the codebase.

# 12. Central authorization service

Create:

```java
public interface AuthorizationService {

    void requirePermission(
        CurrentUser user,
        Permission permission
    );

    void requireOrderAccess(
        CurrentUser user,
        Order order,
        OrderAction action
    );
}
```

With:

```text
CodeBasedAuthorizationService
```

as the initial implementation.

This becomes the abstraction boundary where Cerbos could eventually be introduced.

---

# 13. Tenant security

Every order belongs to a tenant.

For example:

```text
Alice
tenant=A

Order 100
tenant=A

Order 200
tenant=B
```

Alice requesting Order 200 must fail regardless of her other permissions.

Where possible, enforce this during retrieval:

```java
findByIdAndTenantId(
    orderId,
    currentUser.tenantId()
)
```

rather than retrieving arbitrary records and filtering afterward.

---

# 14. Ownership security

Customers can operate only on their own resources.

For example:

```text
Alice → Alice's order
ALLOW

Alice → Bob's order
DENY

Alice → Charlie's order
DENY
```

Support users can access orders belonging to their tenant:

```text
support-a → Alice
ALLOW

support-a → Bob
ALLOW

support-a → Charlie
DENY
```

This demonstrates resource-level authorization rather than simply GraphQL-level authorization.

---

# 15. Sensitive GraphQL fields

Use:

```graphql
Order.internalNotes
```

as the field-level security example.

A normal customer might execute:

```graphql
query GetOrder($id: ID!) {
    order(id: $id) {
        id
        description
        amount
    }
}
```

but requesting:

```graphql
internalNotes
```

requires:

```text
ORDER_READ_INTERNAL
```

This demonstrates that permission to access an object doesn't necessarily grant permission to every field on that object.

# 16. React/Vite application

The UI should be both a sample application and a **security demonstration console**.

I'd give it four main screens.

### Login / identity

Authenticate through Keycloak and display:

```text
Logged in as: alice
Tenant: A
Roles: CUSTOMER
```

This makes switching between Alice, support and admin accounts useful during the demo.

### My Orders

Run:

```graphql
query GetMyOrders {
    myOrders {
        id
        description
        amount
        status
    }
}
```

Customers see their own orders.

### Order Management

Support/admin users can browse tenant orders, inspect an order and perform permitted actions.

The UI may conditionally show actions such as:

```text
Edit
Cancel
Delete
View internal notes
```

but backend authorization remains authoritative.

### Security Playground

This is the most useful POC-specific frontend feature.

Provide a textarea containing GraphQL:

```graphql
query GetOrder {
    order(id: "...")
    {
        id
        description
    }
}
```

along with:

```text
Operation name: GetOrder

[Execute]
```

Display:

```text
HTTP status
GraphQL response
GraphQL errors
authenticated user
```

This allows us to demonstrate attacks interactively rather than only through tests.

# 18. Frontend GraphQL organization

```text
frontend/src/graphql/

├── queries/
│   ├── GetOrder.graphql
│   ├── GetMyOrders.graphql
│   └── GetOrders.graphql
│

    ├── CreateOrder.graphql
    ├── UpdateOrder.graphql
    ├── CancelOrder.graphql
```

This has another useful consequence: the approved frontend operations are visible and auditable rather than being arbitrary strings distributed throughout React components.

# 19. Backend testing

Security behaviour should primarily be covered through integration tests.

```text
OperationSecurityIT

✓ allowsKnownOperation
✓ rejectsUnknownOperation
✓ rejectsAnonymousOperation
✓ selectsRequestedOperation
```

Then:

```text
GraphQLCapabilitySecurityIT

✓ allowsExpectedRootField
✓ rejectsUnexpectedRootField
✓ handlesFragments
✓ handlesAliases
```

And:

```text
OrderAuthorizationIT

✓ customerCanReadOwnOrder
✓ customerCannotReadOtherCustomerOrder
✓ supportCanReadTenantOrder
✓ supportCannotReadOtherTenantOrder
✓ adminCannotCrossTenantBoundary
```

Finally:

```text
FieldAuthorizationIT

✓ adminCanReadInternalNotes
✓ customerCannotReadInternalNotes
✓ supportCannotReadInternalNotes
```

Testcontainers should run PostgreSQL during integration tests.

# 24. Final demo

The end-to-end demonstration would be:

```text
1. Login as Alice

2. View Alice's orders
   → ALLOWED

3. Request Bob's order
   → DENIED: ownership

4. Request Tenant B order
   → DENIED: tenant

5. Submit unknown operation
   → DENIED: operation allow-list

6. Rename malicious operation to GetOrder
   → demonstrate why name-only checking is insufficient

7. Enable/use structural validation
   → DENIED: Query.orders isn't permitted for GetOrder

8. Request internalNotes
   → DENIED: field permission

9. Login as Admin A

10. Request internalNotes
    → ALLOWED

11. Admin A requests Tenant B order
    → DENIED: tenant boundary
```

The last case is important: **ADMIN should mean administrator within a tenant, not automatically "can access the entire database."**

# 25. POC completion criteria

I'd consider the POC complete when a fresh checkout can run the whole system, predefined users can authenticate, React can execute the named GraphQL operations, PostgreSQL is initialized automatically, and automated tests demonstrate all four authorization layers:

```text
Operation
   ↓
GraphQL capability
   ↓
Resource
   ↓
Field
```
